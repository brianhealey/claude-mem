# Hosted Server (Beta)

<Warning>
**This is early and moving fast.** The hosted server's capture, recall, metering,
and deletion paths described below are real and tested, but the **UX and developer
experience around them are still being built** — there's no polished dashboard,
onboarding flow, or self-serve signup yet. Expect the *plumbing* to be solid and
the *paving* to be unfinished. Routes, env var names, and the first-key bootstrap
flow may shift as we wire up the dashboard. Pin a version if you're integrating.
</Warning>

The hosted server is the cloud side of claude-mem: a Postgres-backed HTTP service
(`/v1`) plus a separate BullMQ generation worker. Where the local plugin keeps
memory in `~/.claude-mem/claude-mem.db` on your machine, the hosted server keeps
it per **team** and per **project** in Postgres, and exposes it back to any MCP
client over an authenticated link.

Three capabilities landed together and are documented here:

## The shape of the system

```
 Claude Code (or any MCP client)
        │  Authorization: Bearer cm_...
        ▼
 ┌─────────────────────────────┐        ┌──────────────────────────┐
 │  HTTP server  (/v1)          │  jobs  │  BullMQ generation worker │
 │  - auth (api-key mode)       ├───────▶│  claude-mem server         │
 │  - rate limit / quota / meter │        │    worker start            │
 │  - REST + /v1/mcp recall      │        │  - provider call           │
 │  - data deletion              │        │  - writes observations     │
 └──────────────┬───────────────┘        └────────────┬─────────────┘
                │                                       │
                ▼                                       ▼
        ┌───────────────────────────────────────────────────┐
        │  Postgres  (teams, projects, observations,         │
        │  agent_events, server_sessions, generation jobs,   │
        │  api_keys, usage_events, audit_log)                │
        └───────────────────────────────────────────────────┘
```

Every row is scoped by `(team_id, project_id)`. An API key carries a **team**
(always) and an optional **project** scope; that scoping bounds every read,
write, and delete.

### Authentication

Set `CLAUDE_MEM_AUTH_MODE=api-key` and send `Authorization: Bearer <key>` on every
request. Scopes gate access:

- **Read** endpoints (search, context, recall, usage) require `memories:read`.
- **Write** endpoints (ingest, editing, deletion, job retries) require `memories:write`.
- **Key management and the audit trail** (`/v1/keys`, `/v1/audit`) require
  `keys:manage`. Hook keys never carry it, so a key copied off one machine can't
  list, revoke or mint keys, or read other people's searches. Only the server CLI
  grants it:

  ```bash
  # inside the server container
  bun /opt/claude-mem/scripts/server-service.cjs server api-key create --admin --name "operator"
  ```

  `--admin` adds `memories:read`, `memories:write` and `keys:manage` to any
  `--scope` list you pass.

Keys are stored as SHA-256 hashes in the `api_keys` table; the raw `cm_...` value
is shown exactly once, at mint time.

## Remote authenticated MCP recall

`/v1/mcp` is a streamable-HTTP [MCP](https://modelcontextprotocol.io) server. It's
the secure link a user pastes into Claude Code to recall their cloud memory. It is
**read-only** and authenticated by the same API key as the REST routes
(`memories:read`); the key's team — and project, if the key is project-scoped —
bounds every read.

```bash
claude mcp add --transport http claude-mem <server-base>/v1/mcp \
  --header "Authorization: Bearer cm_..."
```

Three tools are exposed, each mirroring an existing REST path:

| Tool      | Arguments                          | Returns |
|-----------|------------------------------------|---------|
| `search`  | `{ projectId, query, limit? }`     | Matching observations (full-text search). |
| `context` | `{ projectId, query, limit? }`     | Observations **plus** a concatenated `context` string ready for prompt injection. |
| `recent`  | `{ projectId, limit? }`            | The newest observations for a project. |

<Note>
The transport is **stateless** — one MCP server + transport per request — so it
needs no session affinity behind a load balancer. Mutating tools are
intentionally absent: a pasted recall link can never write or delete. Every read
is written to `audit_log` as an `observation.read` event, the same as
`POST /v1/search`.
</Note>

## Connecting a client: key issuance + connect

Two routes turn "I have a server" into "Claude Code is recalling my cloud memory":

- **`POST /v1/keys`** (requires `keys:manage`) mints an API key for the caller's
  team and returns a paste-ready connect command. The raw key appears **once**.
  Body: `{ "label"?: string, "expiresInDays"?: number, "scopes"?: string[] }`.
  `scopes` defaults to `["memories:read"]`; pass
  `["memories:read", "memories:write"]` for a key that can also capture. A key
  can grant only scopes it holds, and never `keys:manage`, which only the server
  CLI grants.

  ```json
  {
    "id": "...",
    "apiKey": "cm_...",
    "label": "laptop recall",
    "scopes": ["memories:read"],
    "expiresAt": null,
    "mcpUrl": "https://<host>/v1/mcp",
    "connectCommand": "claude mcp add --transport http claude-mem https://<host>/v1/mcp --header \"Authorization: Bearer cm_...\""
  }
  ```

- **`GET /v1/connect`** (requires `memories:read`) returns the same command with a
  `<YOUR_API_KEY>` placeholder — a GET never mints. The `mcpUrl` is built from
  `CLAUDE_MEM_PUBLIC_URL` (recommended when behind a proxy or load balancer) or,
  failing that, the request host.

<Warning>
**First-key bootstrap is the rough edge.** There is a dashboard, but signing in to
it takes a key, and `POST /v1/keys` itself requires `keys:manage`. So a team's
*very first* key comes from the server CLI (`server api-key create --admin`).
better-auth's `apiKey()` plugin exists but writes to a different store than the
Postgres `api_keys` these routes authenticate against — wiring the better-auth
org → team mapping is the remaining piece, and the biggest part of the devex work
still ahead.
</Warning>

## Dashboard

The server serves a dashboard at `<server-base>/dashboard`. Sign in by pasting an
API key; the page then calls the same `/v1` routes documented here, so it shows
exactly what that key can reach and nothing more.

| Tab | What it does | Scope needed |
|-----|--------------|--------------|
| **Memories** | Browse recent observations (new ones appear as they are generated), search with matches highlighted, filter by folder, kind, session or date, read one in full, export as JSON or Markdown. Write, edit or delete one. | `memories:read` (write, edit and delete need `memories:write`) |
| **Sessions** | List sessions; open one to see its summary and a timeline of captured events, each with the memories generated from it and its raw payload on request. | `memories:read` |
| **Pipeline** | Job counts by status, the provider and model last used, median capture-to-memory time, token and memory usage, per-lane queue depth, failed jobs grouped by reason, retry one or all. | `memories:read` (retry needs `memories:write`) |
| **Value** | What memory costs against what it plausibly saves: tokens spent generating (measured), tokens handed back to agents and the raw tool output those memories stand in for (both estimated from text length), per day, with compression, recall counts, how many searches, session-start context reads and prompt lookups came back empty, how many memories handed over unasked were later searched for, and the most-recalled memories. | `memories:read` |
| **Keys** | List the team's keys with their label and when each was last used, create a read-only or read-and-write key, revoke a key. | `keys:manage` |
| **Audit** | The team's audit trail: reads and searches, memories written, edited and deleted, keys created and revoked, jobs retried. | `keys:manage` |

<Warning>
Set `CLAUDE_MEM_PUBLIC_URL` (or `CLAUDE_MEM_ALLOWED_ORIGINS`) to the address
people open the dashboard at. The server refuses browser requests from any
origin it has not been told about, so without it the page loads but every
search, save, delete and retry fails with `CORS not allowed`. This only sets
which browser origins may call the server: hooks and proxies that reach it by an
internal name keep working.
</Warning>

<Note>
The key is kept in the browser tab's session storage, or in local storage if you
tick **Remember on this device**. Serve the dashboard over HTTPS anywhere the
network is not trusted: the key is sent as a bearer header on every request.
</Note>

The Value tab's "rediscovery avoided" is a proxy, not a measurement: it is the
size of the tool output behind each recalled memory, and assumes the agent would
otherwise have redone that work. A memory that was only listed in a
session-start block (a `/v1/context` read with no query) is credited with its
title line on both sides, so it nets to nothing: the agent was shown a line, not
the memory. Reads made from the dashboard itself are left
out of it (the page sends `X-Claude-Mem-Client: dashboard`, recorded on its audit
rows).

The usage figures on the Pipeline and Value tabs come from `usage_events`, which the
generation worker only writes when it runs with `CLAUDE_MEM_USAGE_METERING=1`.

`/v1/search` matches on the full-text index and, for queries of up to 128
characters, also on a plain substring, so a word inside a file name such as
`registries.yaml` is found; substring-only matches rank after full-text hits. A
query of several words that fewer than three memories match whole is widened:
memories holding at least half of its terms (four are always enough) are added
after the whole matches. A query of more than eight words, such as a prompt, goes
straight to the widened search, still ranking whole matches first. This is still
term matching, not semantic search.

With `CLAUDE_MEM_SEMANTIC_INJECT=true` in the client's settings, the prompt hook
asks `/v1/context` for memories matching each prompt (up to
`CLAUDE_MEM_SEMANTIC_INJECT_LIMIT`, default 5) and injects them, leaving out
memories the current session wrote itself. These reads are marked
`purpose: "prompt"` in the audit trail. The hook passes
`excludeContentSessionId` and `excludeKinds` so the server leaves those rows
out itself: what `/v1/context` returns and records is then exactly what was
injected, and the Value tab does not count a lookup that only found the
session's own work as a recall.

`<private>` sections are removed from the prompt before it leaves the client,
and the server strips them again, so they are never searched for or stored in
the audit trail. A prompt with too little left after that gets no lookup, and
neither do prompts recorded by the transcript watcher, whose result is never
injected. `CLAUDE_MEM_SEMANTIC_INJECT_FORMAT=index` has no effect in server
runtime: an index points the agent at `get_observations`, which cannot resolve
server memory ids, so the hook always injects the memories themselves.

A compaction removes the session's earlier work from the agent's context, so
after one the hook also passes `excludeContentSessionSince`, the time of the
last compaction (recorded by `SessionStart` after a compaction, and by Codex's
`PostCompact` for the main thread). The server then leaves out only the session's memories from
after that time; those from before it can be injected, and count as recalls,
like any other memory. A memory is dated by the events it was generated from.

The Value tab's "Handed over, then searched for" counts memories given to an
agent unasked (at session start or with a prompt) that an agent's own search
returned afterwards. It is the only sign of use the audit trail holds, and a
lower bound: an agent can use a memory without searching for it.

**Retry all** on the Pipeline tab asks for a second click naming how many jobs it
will requeue, since each one is another provider call. Jobs that failed because
their key was revoked or their scope did not match are left alone: a retry would
fail the same way.

## Paid-readiness: rate limiting, quotas, metering

These guards run **after** auth and are **opt-in via environment variables**. Unset
(the default) means no rate limit, no quota, and no metering — behavior is
identical to a server without them. Every guard **fails open**: a backing-store
error never blocks a legitimate request.

| Env var | Effect | Response when exceeded |
|---------|--------|------------------------|
| `CLAUDE_MEM_RATE_LIMIT_PER_MIN` | Max requests per **API key** per minute. | `429` with `Retry-After` and `X-RateLimit-*` headers. |
| `CLAUDE_MEM_MONTHLY_REQUEST_CAP` | Max requests per **team** per calendar month (UTC). | `402 quota_exceeded`. |
| `CLAUDE_MEM_MONTHLY_TOKEN_CAP` | Max provider **tokens** per team per month. Gates **writes only** — reads stay open so a team over budget can still recall. | `402` at the cap. |
| `CLAUDE_MEM_USAGE_METERING=1` | Records one `request` usage event per authenticated call (fire-and-forget). | — |

Token and observation metering is written to the same `usage_events` table from
the generation worker, so usage reflects real provider spend, not just HTTP calls.

`GET /v1/usage` returns the caller team's per-kind totals for the current month:

```json
{ "since": "2026-06-01T00:00:00.000Z", "usage": { "request": 1280, "observation": 44 } }
```

<Note>
"Gates writes only" is deliberate: ingestion is what drives generation, which is
what costs tokens. A team that blows its token budget can still **read** its
existing memory — you never lock someone out of their own data over billing.
</Note>

## Data deletion (forget)

Right-to-erasure. Both routes require `memories:write` and are scoped to the
caller's team. Both write an `audit_log` entry.

- **`DELETE /v1/memories/:id`** — delete a single observation; its
  `observation_sources` cascade. Returns `404` if no such observation exists for
  the team. Audited as `observation.deleted`.

- **`DELETE /v1/projects/:projectId/memory`** — purge **all** captured content for
  a project in one transaction: observations, raw agent events, server sessions,
  and generation jobs. The project shell (config/membership) is kept so the team
  can keep using it. Returns per-table `counts`. Returns `404` if the project
  doesn't belong to the team. Audited as `project.memory_purged`.

  ```json
  { "purged": true, "projectId": "...", "counts": { "observations": 42, "agentEvents": 17, "sessions": 3, "jobs": 17 } }
  ```

<Note>
Deletion is team-scoped at the SQL layer, so a key can only ever erase its own
team's data — a cross-team or nonexistent `projectId` returns `404` rather than a
misleading success.
</Note>

## Event generation semantics

Ingestion (`POST /v1/events`) accepts two query flags that control observation
generation:

- `generate=false` — write the event but do **not** enqueue a generation job.
- `wait=true` — return the `generationJob` descriptor so callers can poll
  `GET /v1/jobs/:id` for completion.

Without `wait=true`, the response includes the new event row plus a best-effort
`generationJob` field. With `wait=true`, that field is always populated (or `null`
only when generation was explicitly disabled). The actual provider call happens in
the separate BullMQ worker (`claude-mem server worker start`) — the HTTP path
**never blocks** on a provider response.

### Generation concurrency

By default the generation worker processes one job at a time in each of its two
lanes: `event` (per-event observations) and `summary` (session summaries). If
events arrive faster than one job at a time can process them, jobs still complete
but the backlog grows, and observations land hours after the work they describe.
Set `CLAUDE_MEM_SERVER_GENERATION_CONCURRENCY=N` on the generation worker to run up
to N jobs in parallel **per lane**. Both lanes use the value, so one worker process
can have up to 2N provider calls in flight. Size N against your provider's rate
limit. Values above 64 are clamped to 64, and invalid values are ignored with a
warning.

If a worker stops making progress, stale processing locks can be reclaimed for
another attempt. Each attempt may persist observations or report a failure only
while it still owns the Postgres processing lock. A response from a reclaimed
attempt is discarded so it cannot complete or fail the replacement attempt.
This ownership check also applies to session summaries and does not hold a
database lock during the provider call. Recovery may still require another paid
provider call; it does not guarantee exactly-once provider execution.

### Fewer generation calls

Three things keep the worker from making one provider call per tool call.

**Skipped tools.** Events from navigation and bookkeeping tools (`Glob`, `LS`,
`ToolSearch`, `ScheduleWakeup`, the task-list tools, and Serena's overview and
memory-reading tools) are stored but get no generation job. `TodoWrite` and
`ListMcpResourcesTool` are already dropped by the hook's `CLAUDE_MEM_SKIP_TOOLS`,
so they never reach the server. Set
`CLAUDE_MEM_SERVER_GENERATION_SKIP_TOOLS` on the **server** to a comma-separated
list of tool names to replace the default list, or to an empty string to
generate for every tool.

**Batching.** An event that belongs to a session is published to the queue
with a delay, and the first of a session's event jobs to run takes the session's
other queued event jobs with it, so one call covers several events. Every memory
from that call is linked to all of the events it covered, and each event's job
completes together.

| Setting | Set on | Default | Effect |
|---------|--------|---------|--------|
| `CLAUDE_MEM_SERVER_GENERATION_BATCH_WINDOW_MS` | server | `30000` | How long an event waits for its neighbours (0 to 300000). Memories appear this much later. `0` publishes immediately. |
| `CLAUDE_MEM_SERVER_GENERATION_BATCH_MAX_EVENTS` | generation worker | `8` | Most events one call covers (1 to 32). `1` keeps one call per event. |

If a batched call fails, every job in it follows the same retry rule as the job
that carried it.

**Repeats.** The model is shown the titles of the memories the session already
has and asked not to record the same finding again; a memory whose title
repeats one of them is dropped.

### Custom generation provider (advanced)

The generation worker ships with `claude`, `gemini` and `openrouter` providers, and
each one reads a single set of credentials from its environment. If your deployment
needs something else, such as a different key per project, set
`CLAUDE_MEM_SERVER_PROVIDER=custom` and point `CLAUDE_MEM_CUSTOM_PROVIDER_MODULE`
at a JavaScript module. The module must export `createProvider(helpers)`, which
returns an object with a `generate(context)` method. `helpers` gives the module this
server's prompt builder, its Anthropic client (`ClaudeObservationProvider`, which
accepts a `baseUrl`), its retryable error class, the resolved `maxOutputTokens`, and
an `apiVersion` (currently `1`) that changes whenever any of those contracts
change.

<Warning>
The module runs inside the generation worker with everything that process holds:
the database URL, every provider key and the Redis credentials. Treat it like any
other code you deploy. The path is read only from the process environment, never
from `settings.json` or an API route. It must be an absolute path, and the worker
logs the path and the file's sha256 when it loads the module.
</Warning>

## Endpoint reference

All endpoints are mounted under `/v1`; legacy worker routes remain under `/api`.

```
GET    /healthz
GET    /v1/info
GET    /dashboard                 # web dashboard (signs in with an API key)
GET    /v1/whoami                 # team, project scope and scopes of the key
GET    /v1/projects               # projects the key can read
GET    /v1/folders?projectId=     # folders and kinds in a project, with counts
GET    /v1/sessions?projectId=    # a project's sessions, newest first
GET    /v1/sessions/:id/events    # a session's events and the memories made from each
POST   /v1/sessions/start
POST   /v1/sessions/:id/end
GET    /v1/sessions/:id
POST   /v1/events                 # ?generate= ?wait=
POST   /v1/events/batch
GET    /v1/events/:id
POST   /v1/memories
GET    /v1/memories?projectId=    # page through observations (limit, offset, serverSessionId, folder, kind, createdAfter, createdBefore)
GET    /v1/memories/head          # count and newest timestamp, for polling
PATCH  /v1/memories/:id           # edit an observation's content or kind
DELETE /v1/memories/:id           # forget one observation
POST   /v1/search
POST   /v1/context
ALL    /v1/mcp                    # remote authenticated MCP recall
GET    /v1/jobs                   # generation jobs (status, limit, offset)
GET    /v1/jobs/summary           # job counts, failures by reason, last provider, latency
POST   /v1/jobs/:id/retry
POST   /v1/jobs/retry-failed      # requeue all failed jobs, optionally for one reason
POST   /v1/keys                   # mint a key (keys:manage); read-only by default
GET    /v1/keys                   # list the team's keys, metadata only (keys:manage)
DELETE /v1/keys/:id               # revoke a key; not the caller's own (keys:manage)
GET    /v1/audit                  # the team's audit trail (keys:manage; limit, offset, action)
GET    /v1/connect                # connect command with key placeholder
GET    /v1/usage                  # usage totals for this month and today
GET    /v1/value?projectId=       # daily cost and estimated savings of recall (days=7..90)
DELETE /v1/projects/:projectId/memory   # purge a whole project
```

## What's solid vs. what's coming

<Note>
**Solid today:** Postgres-backed multi-tenant storage, api-key auth with
read/write scopes, the `/v1/mcp` recall link, opt-in rate limiting + quotas +
metering, and audited data deletion. All covered by the Postgres-gated e2e suite.

**Still being built (UX / devex):** a session-gated first-key bootstrap (the
dashboard manages keys but still needs one to sign in), self-serve onboarding, a billing/plan UI on top of the metering
primitives, and a smoother "connect Claude Code to my cloud memory" flow than
pasting a CLI command. These are the next focus — the primitives above are the
foundation they'll sit on.
</Note>
